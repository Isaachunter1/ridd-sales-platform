# server/ — the RIDD server on Cloud Run

One Express service, one container, one deploy. It runs the scheduled jobs (BigQuery → Supabase) and the few HTTP endpoints that need a secret. `docs/ARCHITECTURE.md` is the why; this file is the how.

```
server/
├── index.js            mounts every services/*/index.js: routers under /api, POST /jobs/<name> per job
├── config/             env.js (the only process.env reader) · supabase.js · bigquery.js
├── middleware/         apiToken.js (X-API-TOKEN) · auth.js (Supabase JWT + role) · log.js · error.js
├── runtime/            job.js (the wrapper) · lock.js (job_runs) · heartbeat.js · slack.js · killswitch.js
├── services/<domain>/  index.js exports { router, jobs } · jobs/*.js · functions/*.js + *.sql
├── scripts/            run-job.js · schedules.js
├── test/               node:test fixtures
├── Dockerfile · cloudbuild.yaml · .env.example
└── infra/              GENERATED by scripts/schedules.js (scheduler.yaml, scheduler.sh)
```

## Run it locally (5 minutes)

```bash
cd server
cp .env.example .env            # fill in SUPABASE_*, API_TOKEN, GCP_SA_JSON (same values the Netlify functions use)
npm install
npm test                        # fixture tests — no network
npm run dev                     # http://localhost:8080/healthz
npm run job -- ops-stats --dry  # queries RevHawk, writes server/dryrun/indicators/ops-stats.json, touches nothing else
```

Kick a job over HTTP the way Cloud Scheduler will:

```bash
curl -X POST localhost:8080/jobs/ops-stats -H "X-API-TOKEN: $API_TOKEN"
curl localhost:8080/api/sync-status
```

## Deploy with the web consoles

Everything below is one-time. After it, **a merge to `main` is a deploy.**

### 1. Supabase — the `job_runs` table

SQL Editor → paste `migrations/20261020_job_runs.sql` → Run. (It is append-only; a change to the table is a new migration, never an edit.)

### 2. Google Cloud — enable the APIs

Console → *APIs & Services → Enable APIs*. Enable: **Cloud Run**, **Cloud Build**, **Artifact Registry**, **Secret Manager**, **Cloud Scheduler**.

### 3. Secret Manager — the secrets

*Security → Secret Manager → Create secret*, one per row. Names must match exactly:

| Secret | Value |
| --- | --- |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Settings → API → service_role |
| `API_TOKEN` | any long random string (e.g. `openssl rand -hex 32`) — Cloud Scheduler will send it |
| `GCP_SA_JSON` | the RevHawk service-account key file, whole JSON (the one `GCP_SA_JSON` holds in Netlify today) |
| `SLACK_ADMIN_WEBHOOK` | the admin channel's incoming webhook (optional — leave out for logs only) |

### 4. Artifact Registry — where images live

*Artifact Registry → Create repository*: name `ridd`, format **Docker**, region `us-central1` (or whatever you pick — use the same region everywhere below).

### 5. Cloud Build — the trigger

*Cloud Build → Triggers → Connect repository* (GitHub, pick the repo, authorise). Then *Create trigger*:

| Field | Value |
| --- | --- |
| Name | `ridd-server-main` |
| Event | Push to a branch |
| Branch | `^main$` |
| Included files filter | `server/**` (so app-only commits don't rebuild the server) |
| Configuration | **Cloud Build configuration file (yaml)** — location `server/cloudbuild.yaml` |
| Substitution variables | `_SERVICE=ridd-server`, `_REGION=us-central1`, `_REPO=ridd` |

Permissions (*Cloud Build → Settings → Service account permissions*): turn ON **Cloud Run** and **Service Accounts**. That gives the build SA `run.admin` + `iam.serviceAccountUser`.

Click **Run** on the trigger once. It builds the image, pushes it, and creates the Cloud Run service `ridd-server`. The first revision boots **unconfigured** — `/healthz` returns `configured:false` and lists what's missing. That's expected; step 6 fixes it.

### 6. Cloud Run — variables and secrets

*Cloud Run → ridd-server → Edit & deploy new revision → Variables & Secrets*:

**Environment variables** (plain):

| Name | Value |
| --- | --- |
| `SUPABASE_URL` | `https://<project-ref>.supabase.co` |
| `SUPABASE_ANON_KEY` | the public anon key |
| `REVHAWK_PROJECT_ID` | `revhawkdataconnect` |
| `REVHAWK_DATASET` | `org_ridd_pest_control_3f4149` |
| `GCP_JOB_PROJECT` | your GCP project id (where BigQuery queries bill) |
| `CORS_ORIGINS` | `*` for the POC; later the Netlify URLs, comma-separated |
| `SITE_URL` | the app's URL (optional) |

**Secrets exposed as environment variables** — *Reference a secret*, one per row from step 3: `SUPABASE_SERVICE_ROLE_KEY`, `API_TOKEN`, `GCP_SA_JSON`, `SLACK_ADMIN_WEBHOOK`. Version: **latest**. The console will offer to grant the runtime service account *Secret Manager Secret Accessor* — accept.

Check the *Container* tab matches `cloudbuild.yaml` (it will after the first trigger run): request timeout **3600 s**, min instances **1**, concurrency **10**, memory **2 GiB**, CPU **always allocated**. Then **Deploy**.

Open `https://<service-url>/healthz` → `{"ok":true,"configured":true,...}`. Copy the service URL; you need it twice more.

### 7. Cloud Scheduler — the cron table

The cron table lives in the code (each job's `schedule` field). Generate and apply it from your machine (needs `gcloud` signed in):

```bash
cd server
SERVICE_URL=https://<service-url> GCP_PROJECT=<project-id> GCP_REGION=us-central1 npm run schedules -- --apply
```

Without `--apply` it only writes `server/infra/scheduler.yaml` + `scheduler.sh` so you can read what it would do. Prefer the console? Open `scheduler.yaml` and create each entry by hand in *Cloud Scheduler → Create job*: HTTP, POST, the URI shown, header `X-API-TOKEN` = the secret's value, timezone `America/New_York`. The cron table in Cloud Scheduler is otherwise never edited by hand.

### 8. Netlify — point one route at Cloud Run

In `netlify.toml`, **above** the `/api/*` rules that still point at Netlify functions, add the two redirects for the routes that moved, then delete their old entries:

```toml
# ── Cloud Run (the port, Oct 2026) ──────────────────────────────────────
[[redirects]]
  from = "/api/sync-status"
  to   = "https://<service-url>/api/sync-status"
  status = 200
  force = true

[[redirects]]
  from = "/api/jobs/*"
  to   = "https://<service-url>/api/jobs/:splat"
  status = 200
  force = true
```

Open the app → header sync pill → health sheet. It now reads through Cloud Run. Once one scheduled `ops-stats` run has landed in `job_runs` and the file in the bucket matches, delete `ops-stats-now.js`, `ops-stats-scheduled.js`, `ops-stats-background.js`, the `[functions."ops-stats-scheduled"]` block and the `/api/ops-stats-now` redirect from Netlify. No app code changes — the tab only reads the file. Record it in `MIGRATION.md`.

## The port, job by job

Every later job is this, with a different name:

1. `services/<domain>/jobs/<name>.js` wrapped in `job()`, SQL in `functions/*.sql`, pure computation in `functions/*.js` with a fixture test.
2. `npm run job -- <name> --dry` → diff `server/dryrun/<path>` against the Netlify output for the same window. Identical, or explain the difference in the PR.
3. Merge → the trigger deploys. `npm run schedules -- --apply` adds the Scheduler entry.
4. Watch one scheduled run land in `job_runs` and in Slack.
5. Delete the Netlify function(s) and their `[functions.*]` block + redirect. Update `MIGRATION.md`.

## Where to look when something is wrong

| Symptom | Look at |
| --- | --- |
| Slack says a job FAILED | Cloud Logging, filter `jsonPayload.job="<name>"` — the stack is there; the Slack line is the summary |
| "A run is already in progress" | `select * from job_runs where status='running'` — a dead run holds the lock until the 5 a.m. kill switch, or mark it `stale` yourself |
| `/healthz` says `configured:false` | Cloud Run → Variables & Secrets — the response names the missing variable |
| Scheduler shows failures | Cloud Scheduler → the job → logs. 401 = `X-API-TOKEN` header wrong; 409 = overlapping runs, lengthen the schedule; 5xx = read the job's log |
| Numbers look wrong | `job_runs.summary` + `version` say which build produced them; `dryrun` the job locally against the same window |
